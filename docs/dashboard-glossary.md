# Словарь Prompt Radar

## Основные сущности

### Request / запрос

Один вызов ИИ-агента. В прототипе request имеет OpenAI-compatible структуру и
содержит массив сообщений.

### Prompt

Текстовая инструкция или вопрос внутри request. В request могут находиться
system prompt, история диалога, RAG-контекст и текущий вопрос пользователя.

### OpenAI-compatible payload

JSON стандартного вида:

```json
{
  "model": "model-name",
  "messages": [
    { "role": "system", "content": "..." },
    { "role": "user", "content": "..." }
  ]
}
```

Совместимость означает формат API, а не обязательное использование моделей
OpenAI.

### Intent

Текущая цель пользователя, очищенная от system prompt, истории и лишнего
контекста.

Пример:

```text
Полный payload:
регламент + найденные документы + история + вопрос

Intent:
«Покажи выигранные тендеры за месяц»
```

### Intent extraction

Процесс выделения intent из payload.

### Taxonomy

Заранее заданный справочник известных бизнес-сценариев. У сценария есть:

- идентификатор;
- название и описание;
- действие;
- домен;
- системы;
- типичные ручные шаги.

### Action

Что хочет сделать пользователь: найти, написать, создать, обновить,
проанализировать, запланировать и так далее.

### Domain

В какой предметной области выполняется задача: почта, CRM, проекты, HR,
календарь, база знаний и другие.

### Scenario

Конкретный устойчивый способ использования агента.

Примеры:

- сводка писем за день;
- создание тикетов из входящих писем;
- карточка клиента в CRM;
- аналитика компании из открытых источников.

### Classification

Выбор action, domain и scenario для intent.

### Confidence

Оценка уверенности классификатора. Это не вероятность бизнес-успеха и не
качество ответа агента.

### UNKNOWN

Классификатор не нашёл достаточно доказательств для известного сценария.
UNKNOWN лучше неправильного уверенного ответа.

### Fallback

Следующий, обычно более дорогой способ обработки UNKNOWN или запроса с низкой
уверенностью.

### Embedding

Числовой вектор, описывающий смысл текста. Семантически похожие запросы должны
получать близкие векторы.

В текущем checkpoint embeddings не используются.

### Clustering

Автоматическое объединение похожих embedding в группы без заранее заданного
точного label. Нужен для поиска новых сценариев.

В текущем checkpoint полноценный clustering не реализован.

### Gold labels

Эталонные labels, созданные заранее для проверки классификатора. Они не
передаются алгоритму во время предсказания.

## Operational metrics

### Outcome

Технически зафиксированный результат выполнения request.

Возможные значения:

- `success`: задача завершилась успешно;
- `partial`: выполнена только часть;
- `error`: выполнение закончилось ошибкой;
- `unknown`: результат невозможно подтвердить по доступным данным.

Outcome не равен экономической пользе. Он только один из её сигналов.

### Tool call

Обращение агента к внешнему инструменту или корпоративной системе.

Примеры:

- поиск писем;
- чтение CRM;
- создание задачи;
- обновление тикета.

Большое количество tool calls не означает большую пользу. Это активность и
дополнительные затраты.

### Tool error rate

Доля tool calls со статусом `error`:

```text
ошибочные tool calls / все tool calls
```

### Tokens

Единицы текста, которые обрабатывает модель.

- input tokens: входной контекст;
- output tokens: ответ;
- total tokens: сумма input и output.

Tokens являются показателем нагрузки и затрат, а не пользы.

### Latency

Время выполнения одного request.

### P95 latency

Значение, быстрее которого завершились 95% запросов. Оставшиеся 5% выполнялись
дольше.

### Repeat / повтор

Новый request, сделанный потому, что предыдущая попытка не дала полного
результата.

### Repeat rate

```text
повторные запросы / все запросы
```

Высокий repeat rate может означать ошибки, неполные ответы или неудобный UX.

### Feedback

Оценка пользователя:

- `1`: положительная;
- `0`: нейтральная;
- `-1`: отрицательная;
- `null`: оценки нет.

### Active users

Количество уникальных пользователей за весь выбранный период.

### MAU

Monthly Active Users. В многомесячной выборке dashboard показывает среднее
количество уникальных пользователей в месяц.

## Экономические термины

### Task / задача

Исходный запрос вместе со всеми переформулировками. Спрос считается по задачам:
пользователь, переспросивший трижды, создал одну единицу работы, а не три.
Сценарий берётся у первой попытки, результат — у последней.

### Manual time

Оценка времени, которое потребовалось бы человеку для ручного выполнения
сценария. Задаётся посценарно в `taxonomy.json` — от 12 до 95 минут.

В demo это предположение, а не измерение.

### Potential Value

Верхняя proxy-оценка ценности, если бы все задачи были выполнены:

```text
Σ по сценариям (задачи сценария × manual time сценария) × стоимость минуты
```

Суммирование по сценариям, а не среднее: редкий дорогой сценарий не должен
растворяться в частых дешёвых.

Это не прибыль, не выручка и не уже сэкономленные деньги.

### Outcome Yield

Коэффициент, уменьшающий Potential до более консервативной оценки:

```text
Success Factor
× (1 − Review Tax)
× Feedback Factor
```

Штрафа за повторы здесь нет: они уже исключены из спроса на уровне задач, а их
токены остаются в TCO. Второй вычет означал бы двойной счёт.

### Review Tax

Доля результата, которую приходится перепроверять или переделывать человеку.
В demo это предположение.

### Realized Value

```text
Potential Value × Outcome Yield
```

Консервативная proxy-оценка подтверждённой части потенциала. На синтетике её
нельзя называть реальной экономией компании.

### Value Gap

```text
Potential Value − Realized Value
```

Показывает, какая часть потенциала не была подтверждена из-за ошибок, повторов,
review tax и других коэффициентов.

Это не буквальные потерянные деньги.

### TCO

Total Cost of Ownership, полная стоимость владения решением.

В demo включает:

- token cost;
- команду;
- инфраструктуру;
- лицензии;
- амортизацию.

### Net Value

```text
Realized Value − TCO
```

### ROI

```text
(Realized Value − TCO) / TCO
```

Положительный ROI в demo означает результат формулы при выбранных
предположениях. Это не измеренный боевой ROI.

### Return per 1 ₽

```text
Realized Value / TCO
```

Показывает proxy-ценность на один рубль полной стоимости.

### Low / Base / High

Три сценария чувствительности предположений:

- `LOW`: консервативный;
- `BASE`: базовый;
- `HIGH`: оптимистичный.

Это не доверительный интервал и не confidence классификатора.

В demo меняются manual time, success factor, repeat penalty, review tax и
feedback factor. Если LOW отрицательный, это показывает зависимость вывода от
предположений.

## Качество классификации

### Evaluated intents

Количество уникальных intent, по которым есть gold labels и выполнена оценка.
Повторяющиеся одинаковые intent не должны искусственно увеличивать accuracy.

### Scenario Top-1 Accuracy

Доля случаев, где первый выбранный scenario совпал с gold label:

```text
правильные top-1 scenario / evaluated intents
```

### Action Accuracy

Доля правильно определённых действий.

### Domain Accuracy

Доля правильно определённых предметных областей.

### Predicted UNKNOWN Rate

Доля evaluated intent, которые baseline оставил без классификации.

### Что accuracy не означает

Accuracy классификации не показывает:

- качество ответа модели;
- долю полезных задач;
- экономию;
- удовлетворённость пользователей;
- ROI.

## Как читать основные графики

### Динамика использования

- столбцы: число запросов за неделю;
- линия: success rate за ту же неделю.

### Результаты выполнения

Donut показывает распределение success, partial, error и unknown.

### Структура TCO

Stacked bar показывает доли компонентов полной стоимости.

### Сравнение каналов

Web Chat и Agent Platform сравниваются по tokens/request, success и repeat.
Более дорогой по токенам канал не обязательно хуже, но требует проверки
результата.

## Самая важная граница

```text
Classification quality ≠ Agent quality ≠ Business value
```

- classification quality: правильно ли мы поняли сценарий;
- agent quality: выполнил ли агент задачу;
- business value: сколько ценности подтверждено относительно стоимости.
