# Prompt Radar: методика оценки AI-агентов

## Главный вопрос

КРОК нужно сравнить не количество запросов или вызовов инструментов, а
полученную ценность с полной стоимостью владения:

```text
Realized Value > Total Cost of Ownership
```

Токены и tool calls показывают активность и затраты. Они не доказывают, что
рабочая задача завершена.

## Три уровня доказательности

| Доступные данные | Что можно утверждать |
| --- | --- |
| Только request payload | Potential Value: верхняя оценка пользы |
| Request + tool trace | Probable Value: задача исполнялась, но результат ещё не подтверждён |
| Request + outcome + повторы + feedback | Realized Value: консервативная оценка реализованной пользы |

Дашборд обязан показывать уровень доказательности. Отсутствующие данные не
заменяются выдуманными нулями или успехами.

## Выделение намерения

Полный OpenAI-compatible payload может содержать историю диалога, RAG-контекст
и документы на десятки тысяч токенов. До классификации Prompt Radar выделяет
текущий пользовательский запрос:

1. последнее содержимое `<user_query>`;
2. пользовательский текст вне `<context>`;
3. последний содержательный `user` message.

Из него строится компактная Intent Capsule: действие, объект, системы,
ожидаемый результат, периодичность, роль и критерий завершения. Документы из
контекста не должны определять категорию запроса.

## Стоимость самой классификации

Классификация — тоже статья расходов, и метод обязан её считать. Намерение
проходит слои от бесплатного к платному и останавливается на первом, который
готов ответить; полное описание — в [architecture.md](architecture.md).

На выборке из 1 500 запросов до модели доходит 56. Разбор всего потока моделью
стоил бы 88 ₽ при цене 139 ₽ за миллион токенов — то есть по сравнению с
основной экономикой конвейер экономит не деньги, а задержку и независимость от
внешнего провайдера. Утверждать обратное значило бы продавать оптимизацию,
которой нет.

Векторный слой добавлен не ради архитектурной красоты: он снижает долю UNKNOWN
с 20,6 % до 17,4 % и поднимает scenario top-1 с 74,1 % до 75,1 % на gold-разметке.

## Potential, Realized и Value Gap

Единица спроса — задача, а не событие. Пользователь, переформулировавший запрос
трижды, создал одну единицу работы. Переформулировки сворачиваются в задачу по
цепочке `repeatOf`: сценарий берётся у первой попытки, результат — у последней.

Для задачи `i`:

```text
PotentialMinutesᵢ = ManualMinutes(scenarioᵢ) × SessionLengthFactorᵢ

OutcomeYieldᵢ =
  SuccessFactorᵢ
  × (1 - ReviewRateᵢ)
  × FeedbackFactorᵢ

RealizedMinutesᵢ = PotentialMinutesᵢ × OutcomeYieldᵢ
```

Отдельного штрафа за повторы в формуле нет намеренно. Повторные попытки уже
исключены из спроса, а сожжённые ими токены остаются в TCO: переспрос стоит
денег и не приносит ценности. Множитель `(1 - RepeatPenalty)` поверх этого
вычитал бы одни и те же повторы дважды.

Для периода:

```text
Potential Value = Σ PotentialMinutes × CostPerEmployeeMinute
Realized Value  = Σ RealizedMinutes  × CostPerEmployeeMinute
Value Gap       = Potential Value - Realized Value
```

`ManualMinutes` задаётся посценарно в `taxonomy.json` и суммируется по
сегментам спроса, а не усредняется: редкий дорогой сценарий не должен
растворяться в частых дешёвых. Нераспознанные запросы получают оценку самого
дешёвого известного сценария, чтобы UNKNOWN не мог раздувать бизнес-кейс.

`ManualMinutes` и `ReviewRate` являются экспертными предположениями. Они
задаются диапазонами low/base/high и должны калиброваться на небольшой выборке
ручного выполнения задач.

### Коэффициент длины сессии

Заказчик масштабирует сэкономленное время длиной заменённой сессии: 0,3 для
короткого обмена репликами, 1 для обычного, 2 для длинной многошаговой работы.
Единственное свидетельство длины, которое несёт операционный лог, — количество
шагов: вызовы инструментов плюс переформулировки после первой.

| Шагов в задаче | Коэффициент | Задач в выборке |
| --- | ---: | ---: |
| 0–1 | 0,3 | 418 |
| 2–4 | 1 | 649 |
| 5 и больше | 2 | 244 |

Пороги стоят на квантилях этого лога. Если объявить длинной каждую задачу от
трёх шагов, «длинными» окажется почти половина выборки, и коэффициент 2
перестанет что-либо означать.

## Полная стоимость

```text
Inference Cost =
  TotalTokens / 1000 × TokenCostPerThousand

TCO =
  Inference Cost
  + амортизация инфраструктуры
  + электричество
  + команда разработки и эксплуатации
  + лицензии
```

Команда не включается в маржинальную стоимость токена, но обязательно входит в
TCO отдельной строкой. Это предотвращает двойной счёт и позволяет отдельно
сравнивать стоимость инфраструктуры и продукта.

Цена инференса взята по ставке заказчика — 139 ₽ за миллион токенов. На
60-дневной выборке это даёт 191 ₽ на 1,38 млн токенов при TCO 495 191 ₽:
**токены составляют 0,04 % полной стоимости**. Вывод неудобный, но именно он и
есть ответ на вопрос «агент жжёт в разы больше токенов, чем веб-чат»: разница в
токенах не двигает экономику, её двигают железо, лицензии и команда.

```text
Net Value   = Realized Value - TCO
ROI         = Net Value / TCO
Return per ₽ = Realized Value / TCO
FTE-months  = RealizedMinutes / (WorkingHoursPerMonth × 60)
```

Если `TCO = 0`, ROI не вычисляется и отображается как «нет данных», а не
`Infinity`.

## Диагностические метрики

- Outcome Yield: какая доля потенциала действительно реализована;
- Value Gap: где теряются деньги;
- Cost per Successful Outcome;
- токены на реализованную минуту;
- repeat rate;
- tool error rate;
- Realized Value и Value Gap по агентам, сценариям и департаментам.

Value Gap раскладывается на провалы, повторные запросы, человеческую проверку и
негативный feedback. Так финансовая оценка превращается в продуктовый backlog.

## Что нельзя заявлять на синтетике

- «мы уже сэкономили X FTE»;
- «боевой ROI равен Y%»;
- «агент повысил качество работы»;
- «этот департамент сэкономил N рублей».

Корректная формулировка: «при указанных допущениях метод оценивает
высвобождаемый потенциал; на боевых логах формулы остаются теми же, а параметры
калибруются».
