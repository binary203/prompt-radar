# Контекст проекта Prompt Radar

Этот файл нужен команде, чтобы одинаково понимать, что именно мы сделали,
какие данные видит прототип и какие заявления можно делать на защите.

## Задача КРОК

Нужно разработать инструмент аналитики запросов к ИИ-агентам. Он должен:

- классифицировать пользовательские запросы по типам задач;
- объединять похожие запросы в сценарии использования;
- делать краткое описание каждой группы;
- показывать частые и растущие сценарии;
- показывать места, где у агента возникают проблемы;
- представлять результат в понятном dashboard.

## Наша идея

Prompt Radar анализирует не отдельный текст в вакууме, а operational event:

```text
запрос пользователя
+ технические метрики
+ вызовы инструментов
+ результат выполнения
+ повторный запрос
+ feedback
```

Это позволяет построить два уровня аналитики:

1. **Аналитика спроса:** какие задачи пользователи пытаются решать и какие
   бизнес-сценарии встречаются чаще.
2. **Аналитика выполнения:** чем закончилась задача, сколько ресурсов потребила
   и где возникают ошибки или повторы.

Финансовая часть dashboard является дополнительной proxy-моделью. Она
показывает, как можно связать сценарии с ручным временем и TCO, но не доказывает
реальную экономию компании на синтетических данных.

## Что поступает на вход текущей версии

Текущий checkpoint читает локальный синтетический файл:

```text
src/data/synthetic/operational-log.jsonl
```

В нём 1 500 событий за 60 дней. Каждое событие содержит:

- дату;
- анонимный идентификатор пользователя;
- роль и подразделение;
- имя агента;
- OpenAI-compatible request с массивом `messages`;
- input, output и total tokens;
- задержку;
- список tool calls;
- outcome;
- feedback;
- ссылку на исходное событие, если запрос является повтором.

Боевой коннектор к инфраструктуре КРОК в прототипе не реализован.

## Как проходит обработка сейчас

```text
Operational event
    ↓
извлечение последнего пользовательского intent
    ↓
детерминированная классификация по taxonomy
    ↓
scenario либо UNKNOWN
    ↓
агрегация usage, outcome, repeats и quality
    ↓
dashboard и proxy-экономика
```

### Извлечение intent

Функция `extractUserIntent`:

- берёт последнее содержательное сообщение пользователя;
- при наличии `<user_query>` использует его;
- удаляет блоки `<context>`, `<source>` и `<documents>`;
- не позволяет большому RAG-контексту определять категорию запроса.

### Классификация

Текущий `classifyIntent` является объяснимым лексическим baseline:

- ищет признаки действия: найти, создать, сравнить, написать и другие;
- ищет признаки домена: почта, CRM, проекты, HR, календарь и другие;
- сравнивает токены запроса с описанием сценария в taxonomy;
- возвращает до трёх labels для составных запросов;
- возвращает `UNKNOWN`, если сильных доказательств нет.

Это не embedding-модель и не обученная нейросеть.

### Группировка сценариев

В текущей демонстрации события группируются по заранее заданной taxonomy после
классификации. Полноценный unsupervised clustering новых запросов пока не
реализован.

### Агрегация

После классификации рассчитываются:

- requests и active users;
- MAU;
- tokens и tool calls;
- success, partial, error и unknown;
- repeat rate;
- weekly trend;
- метрики по агентам и сценариям;
- accuracy относительно gold-разметки.

## Синтетический датасет

Данные разделены на два слоя:

1. `188` разнообразных intent с отдельной gold-разметкой. Они нужны для проверки
   классификации.
2. `1 500` operational events. Они нужны для временных графиков, outcome,
   повторов, latency и экономической модели.

Gold labels применяются только после предсказания и не доступны классификатору.

## Что показывает dashboard

### Верхние KPI

- количество запросов;
- активные пользователи;
- доля успешных outcome;
- repeat rate;
- количество tool calls и доля их ошибок.

### Динамика

Столбцы показывают количество запросов по неделям. Линия показывает success
rate за те же недели.

### Результаты выполнения

Donut показывает доли `success`, `partial`, `error` и `unknown`.

### Экономика

Показываются Potential Value, Realized Value, Value Gap, TCO, ROI и
чувствительность low/base/high. Это proxy на синтетике, а не измеренная
экономия.

### Сравнение каналов

Сравниваются Web Chat и Agent Platform:

- пользователи и запросы;
- tokens per request;
- success rate;
- repeat rate.

### Качество классификации

Показываются top-1 accuracy сценария, accuracy действия, accuracy домена и доля
UNKNOWN.

## Что реально реализовано

- контракты OpenAI-compatible request и operational event;
- воспроизводимый генератор синтетики;
- intent extraction;
- лексический baseline и UNKNOWN;
- агрегация и временные ряды;
- методика proxy-экономики;
- dashboard;
- OpenAI-compatible HTTP-клиент;
- автоматические тесты.

## Что пока является следующим этапом

- кэш классификаций для повторяющихся intent;
- embeddings и prototype similarity;
- отдельная обученная ML-модель;
- подключение LLM fallback к checkpoint;
- clustering для автоматического обнаружения новых сценариев;
- боевой источник данных;
- редактирование финансовых допущений из интерфейса.

## Целевая каскадная архитектура

Идея четырёх уровней подходит как развитие проекта:

1. exact/semantic deduplication и cache;
2. правила и embedding similarity к известным прототипам;
3. компактный классификатор на размеченных данных;
4. локальная LLM для UNKNOWN и низкой уверенности.

Clustering лучше считать отдельным процессом обнаружения новых сценариев, а не
четвёртым или промежуточным слоем классификации.

## Главная честная формулировка

> Мы реализовали воспроизводимый прототип аналитики operational logs
> ИИ-агентов: он извлекает intent, классифицирует запросы, агрегирует outcome и
> показывает результат в dashboard. Синтетика доказывает работу pipeline, но не
> доказывает реальную экономию КРОК.
